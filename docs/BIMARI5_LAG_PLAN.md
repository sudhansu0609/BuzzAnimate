## Diagnosis (measured 2026-09-27, RTX 5060 Ti, DX12, 1600×900 stage)

Measured with a temporary in-crate probe (kept as `docs/probes/zz_perf_probe.rs`,
not compiled; its header says how to run it; see S0), `stage_cost`, and code reading.

### 1. The "ms" in the status bar is not frame cost
`App::render` sets `active.frame_ms = now - last_frame` (app.rs ~10370).
The window sleeps on `ControlFlow::Wait` when idle, so after sitting on a
frame for 2 s, the next click reads ~2000 ms even if that frame took 25 ms.
**The 2253 ms and 600 ms readings are not trustworthy measurements.** The
lag is real (next sections), but this number overstates it and hides where
the time goes.

### 2. Real cost per frame (single pass, grown to buffer scale 4)
| Frame | CPU encode (warm) | GPU raster | Lines |
|---|---|---|---|
| 0 | 23 ms (cold 112) | 20 ms | 4.27 M |
| 20 | 17 ms | 18 ms | 4.05 M |
| 715 | 21 ms | 4 ms | 0.64 M |
| 900 | 75 ms | 9 ms | 1.80 M |
| 4600 | 74 ms | 9 ms | 2.56 M |
| 4700 | 80 ms | 20 ms | 3.15 M |

Playback (every frame in order, as the playhead visits them; encode only):
0–48 median 26 ms, p95 33, max 119; 690–740 median 55 ms; 880–930 median
100 ms. The UI (`build_ui` + tessellate) costs < 1.5 ms: **not the problem**.

### 3. Root cause of the heavy frames: two stamp-cache refusals
Hiding one layer at a time shows that one layer carries almost all the cost:
- frame 715: `Layer_29` costs 52.5 of 54 ms;
- frame 900: `charriotRunning` costs 97.6 of 100.6 ms;
- frame 4700: `charriotRunning` 67 + 12 ms, and `well` 34 ms.

What those layers hold:
- `Layer_29` / `charriotRunning` @900: one instance of **`house8 copy 3`**
  (715 shapes, 196 nested instances, depth 4) placed with a **colour effect**.
- `charriotRunning` @4700: **`VILLAGEbACK1 copy 2`** (2,952 shapes, 561
  instances) with a colour effect, plus six **`road1 copy`** strips rotated
  90° with **unequal x/y scale** (`[0, .268, -.591, 0]`).
- `well` @4700: two **`newTree copy 4`** at **non-uniform scale**
  (1.594 × 1.488, and mirrored −2.198 × 2.052).

`try_stamp_symbol` (`crates/buzz-render/src/document.rs` ~4555) refuses:
- any instance whose composed colour effect is not identity
  (`!inner_ctx.effect.is_identity()`, ~4600). The effect passes down, so
  **every nested child is refused too**, and the whole background subtree
  is re-encoded from scratch every frame;
- any placement that isn't a similarity (`is_orthogonal` check, ~4643).

Both refusals are about correctness of the *current* key
(`SymKey { fingerprint, inner, depth, scale_bits, sealed, stroke_scale_bits }`),
which has no room for an effect or a full linear part. Neither is a
fundamental limit: a key that includes them makes the reuse exact.

### 4. Band mode multiplies that cost, and can trap the stage
- Band mode re-walks the whole scene per band, and in band mode a stamp needs
  ≥ 50% of the instance inside **the band** (H0), so large backgrounds are
  drawn live in every band. With the colour-effect background (~100 ms live),
  8–16 bands means **0.8–2 s per frame**. At buffer scale 1, `stage_cost`
  measured banded frames at 300–900 ms (69 of 199 sampled frames). This
  matches the reported 600 ms / 2253 ms and "the app hanged".
- **Trap:** while `stage_bands > 0`, `wants_whole_frame_ladder` is false,
  so `stage::build_scene` → `DrawCache::reconsider` (the only place the
  buffer scale grows, V3 of `VRAM_ADAPTIVE_BUFFERS_PLAN.md`) never runs.
  A stage that enters bands at scale 1 or 2 never learns that 4× or 8× would
  fit in one pass. It leaves bands only when the *largest band* is under 40%
  of budget (`render_stage_bands`, app.rs ~1886), which a 4M-line frame
  never reaches.
- **Not yet proven:** that the reporter's session actually entered band mode.
  Fresh at 1600×900, the ladder grows 1→4 and fits (probe). Candidate
  entries: zoomed-in view, the 4-pass ladder cap (`stage.rs` ~64) running out
  after 3 grow passes, a scale shrunk by V4 before a heavy frame. S0 settles it.

### 5. Other costs found
- Each grow step (1→2→4→8) throws the frame away and re-encodes it: up to
  3 wasted 100 ms encodes on the first heavy frame after a shrink.
- `stage_cost` predates V2–V5: it never grows the scale (it reports 1×) and
  times only the GPU pass on single-pass frames, not the encode.
  **Its numbers are pessimistic for bands and blind to encode.**
- Renderer rebuild on V4 shrink: 7 ms + 24 ms first render. Not the hang.

### 6. The playhead
Playback is wall-clock (or the audio clock when sound plays,
`Editor::advance_playback`, editor.rs ~1483). At 55–100 ms per frame and
24 fps, each drawn frame advances the playhead 2–3 frames, so it jumps.
Expected to be fixed by S1–S4, but S0 must confirm it isn't also a
timeline-drawing bug.

## S5 (revised 2026-10-01, Opus architect): off-thread encode for playback and seeks
Replaces S5's "cold stamps in playback" and "pipelining" bullets (the "frames 0–100" bullet stands).

### Decisions
- **Dedicated encode thread + stamp pre-build pool** (not a shared concurrent stamp store). Warm encode 10–13 ms + GPU 18–25 ms misses 25 ms, so encode must leave the render thread. One `DrawCache` (`App::lights`) owned by one `buzz-encode` thread and walked in frame order gives the same decisions `build_scene` would (sighting, `seen_off_screen`, ladder, LRU): byte-identical.
- **Pre-build on worker-private caches, install through the main cache.** Workers keep their own `DrawCache` (nested stamps stay warm) and return only the entries they built; the encode thread installs them before each frame. No LRU refactor.
- **Exactness:** without pre-build, byte-identical to render-thread `build_scene` for the same frame order (test). With pre-build, a top-level first sighting becomes a hit instead of a live draw: the same state S9's warm-up produces; S6.3 parity gate covers it.
- **Canonical stamps:** inside a stamp build, nested misses always build (ignore the 2nd-sighting rule), so a stamp's bytes depend only on its `SymKey`, whoever builds it.
- **Ladder:** the encode thread runs `reconsider` as today; `Prepared` carries `scale()`; the render thread calls `grow_to` before `gpu.render`. `over_budget()` ends the pipeline and falls back to bands (S9 sizing should prevent it; log if it happens).
- **Pipeline only while playing a plain stage:** `edit_path` empty, onion off, no Edit Multiple, no painted preview, `stage_bands == 0`, lights inactive or settled (`!cold && !stage_stale && shade_build.is_none()`). Otherwise today's path.

### Architecture
New `crates/buzz-app/src/encode_ahead.rs`: `StageInputs {scene (Arc clone), camera, frame, area_px, scale, buffer_scale}`; `Epoch = (revision, camera bits, area bits, scale, detail, lights_generation, buffer_scale)`; request `(Epoch, first_frame, StageInputs)`; reply `Prepared {epoch, frame, scene, scale, over_budget, lines, encode_ms}` on a bounded depth-2 queue; 3 recycled `vello::Scene`s. The cache is lent via `mem::replace(&mut self.lights, stand_in)` and returned on stop/seek/edit/epoch change.

## S10: exact picture cache (designed by Opus architect, 2026-09-30)
User decision 2026-09-30: a raster cache is allowed **only** with parity vs live ≤2/255 on ≤0.1% px at 1×/4×/16×/40× zoom and mid camera move.

### Decisions
- **Granularity: layer-stack runs.** *Bottom picture* = stage fill (stage.rs:190) + longest bottom run of cacheable layers; optional *upper pictures* (source-over runs above a live layer), max 2. Fewer pictures = less atlas, fewer 8-bit rounding points.
- **Composite inside Vello, one pass.** Each picture is registered with `Renderer::register_texture` (vello 0.9 lib.rs:572) and drawn into the raw scene with `Scene::draw_image`, `Affine::IDENTITY` (not via SceneBuilder output scale), `ImageQuality::Low` (nearest at pixel centres, fine.wgsl:1319-1334) + extend Pad, so it reproduces the texture exactly; live layers are encoded between images; still one `gpu.render` into `Active::target` (app.rs ~11152). Blitter/`Compositor::run` untouched.
- **Pictures are full-target and rendered by the same path** (`gpu.render`, same `area_px`, `scale`, cull, pasteboard base colour): no quantised scale, no cull grid, no pre-camera encoding (the three reasons P2 failed).
- **No reuse across any camera/view change.** Camera tweens (stage.rs:195) and depth parallax (document.rs:2712) move art by fractional px, and S2-rest (a) proved Vello coverage flips under 0.002 px. Camera-moving frames draw live and reach 25 ms only via S5 (culled/chunked stamps) + pipelining.
- **Backdrop readers only in the bottom picture:** a layer with `blend != Normal` (document.rs:3059) or objects with group-blend/additive flags (~1128) may be cached only inside the bottom run, else live.
- **Mask runs are atomic** (mask + all masked layers cached together or live together).
- **Precision:** vello 0.9 `render_to_texture` and the image atlas are Rgba8Unorm only (lib.rs:463, recording.rs:247); atlas max 8192² (vello_encoding image_cache.rs:10; patched copy in `third_party/vello_encoding`).

### Exactness risks
1. Opaque bottom picture rounding: ≤1/255 after upper layers draw over it (P1 proves).
2. Transparent upper pictures: stored unpremultiplied 8-bit, re-premultiplied on read; may exceed 2/255 at low-alpha edges ⇒ if P1 fails, ship bottom-only (`upper=false`).
3. Backdrop reads/masks: rules above, each with its own fixture.
4. A fingerprint missing an input silently freezes animation: P0/P2 prove equal fp ⇒ equal pixels; unknown modifier ⇒ live.
5. Atlas: ≤3× target pixels of the 8192² shared with document bitmaps; allocation failure ⇒ that frame live.
